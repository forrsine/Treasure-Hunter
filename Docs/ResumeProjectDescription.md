# 宝藏猎手：简历项目描述

## 推荐填写方式

**宝藏猎手｜Unity 3D 第三人称动作 Roguelite｜个人项目**  
技术栈：Unity 2021.3、C#、QFramework、uGUI、Addressables、TCP、Protobuf、.NET 9、SQL Server、JSON、ScriptableObject

项目简介：独立开发四职业第三人称动作 Roguelite 原型，完成“清怪成长—击破 5 个宝箱—挑战 Spider King—获得装备并进入下一轮”的单人闭环，并围绕 Unity 客户端岗位持续完善架构、系统 UI、数据持久化和自动化验证。

### 一页简历推荐版

- 基于 QFramework 将角色、技能、背包、装备、金币、商店和任务拆分为 Model/System/Command/Query/Event，配合组件化 `PlayerRuntime` 分离输入、业务规则与 Unity 动画/物理/UI 表现，四职业共用同一运行时逻辑。
- 实现怪物 FSM、Spider King 轻量行为树、四级数据驱动技能和战士蓄力/刺客动作承诺等职业机制；为怪物、投射物、技能特效、掉落和飘字接入对象池，并使用 NonAlloc 物理查询处理高速投射物与范围命中。
- 设计 24 格背包、6 槽装备、金币商店和击杀任务闭环，使用 ScriptableObject 保存静态配置、稳定 ID/DTO 保存运行时数据；穿戴采用原子交换与整套属性差值重算，避免背包失败或反复穿脱导致数据不一致。
- 打通游客 JSON 与 TCP/Protobuf/.NET 9/SQL Server 两套角色数据源，保存成长、背包、装备、金币、限购和任务进度；通过防抖自动保存、事务写入、服务端身份绑定和边界校验处理数据一致性。

### 如果简历空间只能放三条

- 使用 QFramework 与组件化 `PlayerRuntime` 重构四职业玩家流程，将角色、技能、背包、装备、商店和任务拆分为可测试的 Model/System/Command/Query/Event，UI 通过 Query/Event 被动刷新。
- 完成怪物 FSM、Spider King 行为树、技能/投射物/掉落对象池和 NonAlloc 命中检测，并实现四职业差异化战斗、5 箱 Boss 周回以及背包—装备—商店—任务闭环。
- 打通游客 JSON 和 TCP/Protobuf/.NET 9/SQL Server 角色存档，保存成长、背包、装备、金币、限购与任务进度，加入防抖、事务、稳定 ID、服务端身份绑定和数据边界校验。

## 一分钟面试回答

这个项目叫《宝藏猎手》，是我个人开发的 Unity 第三人称动作 Roguelite。核心循环是玩家选择四个职业之一，在主场景清怪、升级并击破宝箱，累计五个宝箱后进入 Spider King Boss 战，击败 Boss 获得装备和金币再继续下一轮。

客户端结构上，我用 QFramework 把权威数据和业务规则放在 Model、System、Command、Query、Event 中，Unity 组件只负责输入、动画、物理和 UI。例如背包、装备、商店和任务都不会直接修改界面数据，而是通过命令处理规则，再用事件刷新 UI。玩家也拆成移动、战斗、生命、成长、技能和表现组件，四职业共用同一个 PlayerRuntime。

工程上我还做了怪物和投射物等对象池、NonAlloc 物理查询、Addressables 本地异步特效、游客 JSON 存档，以及 TCP、Protobuf、.NET 服务端和 SQL Server 的角色持久化。当前网络范围主要是账号和角色数据，不会把它夸大成多人战斗同步。这个项目让我比较完整地练习了玩法、系统 UI、数据驱动、客户端服务端联调和测试边界。

## 面试主线建议

1. **问题**：早期原型的玩家、UI 和数据职责混在一起，系统增加后容易互相影响。
2. **拆分**：用 PlayerRuntime 组件化玩家，用 QFramework 分离权威数据、规则和表现。
3. **完整案例**：选择装备系统或角色存档，讲清楚一条从 UI 到数据源的完整调用链。
4. **性能意识**：说明为什么对怪物、投射物、掉落和特效使用对象池，以及回收时如何重置状态。
5. **边界意识**：主动说明当前网络只覆盖账号与持久化，性能指标仍需真实测量。
6. **下一步**：补完整测试结果、Profiler 基线和自动构建，而不是继续盲目堆系统数量。

## 可展开的两个项目难点

### 难点一：装备与背包一致性

穿戴不是简单地把装备引用放进一个槽。系统必须确认物品类型、目标槽、等级限制和背包状态；更换装备时，新装备离开背包、旧装备回到背包必须作为一个整体成功。完成后重新计算整套装备属性，再用新旧差值更新玩家，避免反复穿脱造成数值漂移。

### 难点二：双数据源角色存档

上层 UI 只调用 `GameApiClient`，游客模式落到带版本号、临时文件和备份的 JSON；在线模式则通过 TCP/Protobuf 进入 .NET 服务端和 SQL Server。连续变化使用防抖保存，领奖和死亡等关键节点立即保存；服务端通过 Session 绑定角色，并校验物品、装备槽、任务状态和数值范围。

这两个案例都能同时展示 C# 设计、Unity 系统整合、数据一致性和异常边界处理。
